# Changelog - Yakuda Connect

### 🚀 v1.2.4

**EN**

* **Debian / Ubuntu / Linux Mint can install WiVRn from the app** (tested on Mint 22.3 "Zena"). Until now the installation tab offered these systems nothing but a set of commands to copy. WiVRn is not in the official Ubuntu sources, but it is packaged in the Linux VR Adventures PPA — the same situation as xrizer on Fedora, and handled the same way: the app asks once before adding a third-party repository, then adds the PPA, refreshes the package lists and installs, all in one visible terminal window. `add-apt-repository` is pulled in via `software-properties-common` if missing.
* **On Debian/Ubuntu/Mint the Flatpak is now the default.** The native route there is not an equal second option but a chain of special cases: the PPA has no build for Ubuntu 24.04 ("noble", the base of Mint 22.x), an OpenVR translation layer is missing anyway, and OpenComposite would have to be built by hand. The Flatpak runs on every release and ships xrizer and OpenComposite. The PPA stays selectable in the dropdown — on releases it builds for, it is the better route (full control, lighthouse trackers).
* **Third entry: "Native (guide)".** Anyone who wants to do it by hand gets the English step-by-step guide opened instead of the app automating a route that differs per release. Afterwards there is nothing else to do: as soon as `wivrn-server` is in the PATH, yakuda-connect picks it up on its own, wherever it came from. The wiki page is wired up for now; once a video is set (`NATIVE_GUIDE_VIDEO_URL`), the button opens the video.
* **`libxcb-cursor0` was never actually installed by the script.** In `pm_install`, `apt-get update` and `apt-get install` were chained with `&&`. If `update` trips over a single broken third-party source — not unusual on a Mint system that has been around a while — it returns an error code and the installation behind it never ran. The trailing `|| true` then swallowed that too, so no error was shown. By hand the same command worked, of course. The two are now decoupled: a failing `update` is reported and the installation proceeds anyway. If the batch install fails (a package name differs on another Debian release), a second attempt follows with exactly the library without which Qt demonstrably will not start.
* **The PPA is checked first — and there is a plan B.** On Linux Mint 22.x (base `noble`), `add-apt-repository` fails with "Cannot add PPA: This PPA does not support noble": the PPA has no build for that Ubuntu release. The app now asks Launchpad beforehand whether packages exist for its own base, instead of walking into it. If there is no connection, it does **not** block — better to try than to refuse wrongly.
* **WiVRn as a Flatpak.** When the PPA has no build, the app offers the Flathub Flatpak; it also appears as a second source in the "WiVRn / Monado" row. It runs on any distribution and ships xrizer and OpenComposite with it, so the GitHub download becomes unnecessary. What it costs is stated plainly: sandboxing, so no SteamVR lighthouse trackers, configuration under `~/.var/app/`, and limited control of the server from yakuda-connect. Detection goes through `flatpak info` — otherwise the row would claim WiVRn is missing while it is running.
* **The Ubuntu codename comes from `/etc/os-release`.** `lsb_release -cs` returns `zena` on Mint, not `noble` — but PPAs follow the Ubuntu base, which is recorded there as `UBUNTU_CODENAME`.
* **On Mint the Ubuntu codename matters.** `lsb_release -cs` returns the Mint name there (`zena`), not `noble`. A hand-written sources line would point nowhere, which is why the install deliberately goes through `add-apt-repository` — it resolves the base release itself.
* **xrizer on apt systems comes from the GitHub release.** The PPA carries no OpenVR translation layer, and without one no SteamVR game starts under Proton. The download built for Fedora is reused: release ZIP into `~/.local/share/xrizer`, no repository, no root. OpenComposite has no comparable release archive and is therefore not offered on apt systems — it can still be built manually and selected in the streaming tab.
* **The WiVRn dashboard is not offered here either**, for the same reason as on Fedora: a second interface on the same config and the same service, redundant next to yakuda-connect. `wivrn-dashboard` would pull `wivrn-server` in anyway; installing the server directly is enough.
* **Package status and post-install verification for apt.** Installed packages are read from `dpkg-query` (only genuinely `installed` ones — a removed package whose config remains no longer counts), updates from `apt list --upgradable`. After a run, every requested package is checked again and the missing ones are named, usually meaning the PPA has no build for this Ubuntu release.

### 🚀 v1.2.3

**EN**

* **Fedora: OpenComposite and xrizer no longer report "no vrclient.so"** — the OpenVR selection showed that warning for a perfectly working installation, and picking such an entry would have written a dead path into WiVRn's `config.json`. Cause is the package layout: Arch (AUR) ships `/opt/opencomposite/bin/linux64/vrclient.so`, while the official Fedora RPM puts it one level deeper at `/usr/lib64/opencomposite/runtime/bin/linux64/vrclient.so` (checked against the RPM's file listing). The app only knew the base folder, which does exist on Fedora but contains no `bin/linux64`. A folder is now resolved to the directory that really holds the library — the known `runtime` subfolder first, then one level down for layouts we don't know yet. Deliberately limited in depth: a full scan of `/usr/lib64` would be noticeable every time the tab opens. The entry keeps its plain name ("OpenComposite", not "runtime") and is marked as *not* auto-detected, because WiVRn does not find a nested folder on its own either.
* **Design: the area behind the cards is recoloured too** — it comes from the QApplication stylesheet (`QStackedWidget`), not from a widget, and was therefore skipped. The result was a recoloured window sitting on a background in the old colour. The same step now also covers dialogs, menus, tooltips and progress bars.
* **Design: theme preview tiles stay untouched** — they show the colours of their own theme. Being recoloured meant the "Default" tile carried the orange tones of "Embers" and all eight looked alike. The same applied to the colour swatches under "Colors".
* **New "Design" section in the settings** — eight themes (Default, Carbon, Nebula, Embers, Grass, Ocean, Rose, Mono), individually adjustable colours for accent, window, sidebar, cards, inner boxes, borders, text, secondary text and stop/delete, a background image behind the window, and a slider for card opacity. Everything applies immediately, no restart.

  How it works: the interface carries roughly 400 hard-coded colour values across about 110 stylesheets. Rather than rewriting each one — a lot of work with a high chance of missing spots that would then sit black on black — the colours are substituted at apply time. Every base value belongs to a role; shades within a role (e.g. `#2e3440` and `#21252b`) keep their lightness distance, so a theme only needs one colour per role. The default theme is a 1:1 mapping and therefore looks exactly as before.

  Green (`#a3be8c`) and yellow (`#ebcb8b`) stay untouched in every theme: "installed" has to stay green and "attention" yellow, otherwise the colour stops carrying meaning. Opacity applies only to cards and inner boxes — on the window background the desktop would show through, and on `color:` it would produce semi-transparent text.
* **Installation tab: buttons now line up in a column** — dropdown (210 px) and button (120 px) have fixed widths, and rows without a choice get a spacer. Previously the longest status text decided where the button landed, squashing its label.
* **xrizer: COPR is the default again** — it is the route the project itself points at. The GitHub release stays as the second source in the dropdown, for when the COPR times out again or disappears as announced.
* **Installation tab re-checks when opened** — the check used to run only at startup, so coming back after installing something in a terminal still showed the old state.
* **Tools: SlimeVR and OscGoesBrrr installable on Fedora** — new "RPM (dnf)" method: the matching RPM is pulled from the newest GitHub release and installed with `sudo dnf install` in a terminal (dnf resolves the dependencies, unlike `rpm -i`). SlimeVR also gains Flathub (`dev.slimevr.SlimeVR`). The method only appears on systems with dnf.
* **Architecture selection for RPM/DEB fixed** — architecture was auto-detected only for AppImages; for any other extension the app took the first match. SlimeVR ships `SlimeVR-aarch64.rpm` BEFORE `SlimeVR-amd64.rpm`, so an ordinary PC would have got the ARM package. It even installs, it just never starts.
* **Release cache keyed per asset type** — it was keyed by repository alone. For OscGoesBrrr (AppImage AND RPM from the same repo) the RPM lookup would have received the cached AppImage URL.
* **VR priority: `setcap`/`getcap` are called with a full path** — both live in `/usr/sbin` (package libcap), which is not in `PATH` in every GUI session, and `pkexec` sanitises the environment anyway. If libcap is missing entirely, the row now reports "unsupported" instead of offering a button that then fails.
* **Installation tab: source and button per component** — every row now has its own "Install" button, and where more than one route exists, a dropdown in front of it (AUR/paru, Fedora repos, COPR, GitHub release). Pulling in just xrizer no longer triggers a run over every package, and a failure no longer leaves you guessing which package stalled. The big button below stays and still installs everything missing — following whichever source the row is set to. The dropdown only appears when there is a real choice.
* **xrizer on Fedora defaults to GitHub** rather than the COPR. The project page says so itself: "This copr will go away after all packages have been reviewed and imported into Fedora." Add the timeouts on top. Anyone who still wants the COPR picks it in the row — a deliberate decision for a third-party repository, with no extra prompt.
* **Fedora: WiVRn Dashboard removed from the installation tab** — it caused trouble there (a second interface on the same `config.json` and the same server) and is redundant when yakuda-connect is running anyway. On Arch it stays part of the usual AUR installation. The terminal update fallback accordingly refreshes only `wivrn` and `opencomposite`.
* **xrizer path on Fedora confirmed** — the COPR project page gives `VR_OVERRIDE=/run/host/usr/lib64/xrizer/runtime` as the Steam launch option. The `/run/host` prefix is just the view from inside the Steam container; on the system it is `/usr/lib64/xrizer/runtime`. That path is now listed explicitly, as is `/usr/lib64/opencomposite/runtime`.
* **Fedora: failed package installs are no longer silent** — the terminal window closes after two seconds, so a dnf error ("nothing provides…", package missing for this Fedora release, COPR without a build) was gone before anyone could read it, while the app still reported success. After the run, every requested package is checked with `rpm -q` and the ones that did not arrive are named in the status line and the log.
* **Fedora: self-built WiVRn or dashboard is recognised** — if there is no matching RPM but the binary is in `PATH`, the row no longer claims the component is missing.
* **xrizer straight from GitHub as an alternative** (reported with a screenshot) — the COPR `@xr-sig/xrizer` is at times effectively unreachable: `copr.fedorainfracloud.org` then delivers less than 1000 bytes per second and dnf gives up after minutes with `Curl error (28): Timeout was reached`. The prompt before installing now has a third button, "Download from GitHub instead", and the same route is offered afterwards when a COPR attempt fails. The release ZIP from `Supreeeme/xrizer` is downloaded into `~/.local/share/xrizer` — no repository, no root, with a progress indicator rather than a terminal window. The `dependencies.zip` asset from the same release is skipped: it is not the program. The wrapper folder inside the archive (`xrizer-v0.5/`) is stripped, otherwise the entry in WiVRn's `config.json` would point one level too high. The swap happens only once the new directory is fully extracted and verified — a half-extracted xrizer would be worse than none, because WiVRn would then point at a broken library. Archives containing `../` or absolute paths are rejected. Since WiVRn does not search `~/.local/share/xrizer` on its own, the app asks whether to set the path as the OpenVR compatibility folder.
* **Fedora: xrizer is installed from the app** (COPR `@xr-sig/xrizer`) — it used to be a notice window with two commands to copy into a terminal by hand. xrizer is now a normal row in the installation tab; the install button enables the COPR and installs the package in the same visible terminal window as everything else. Since a COPR is a third-party repository, the app asks once before enabling it; declining skips only that entry. On dnf4 the `dnf copr` plugin is pulled in automatically if it is missing.
* **Fedora: the terminal update covers every component** — the fallback used when no software center is found only refreshed `wivrn` and `opencomposite`; dashboard and xrizer were missing. The list now comes from the same source as the installation and is filtered to packages that are actually installed, so declining the COPR prompt doesn't produce an error about a missing xrizer in the middle of an update.
* **`install.sh` no longer fails on Linux Mint / Ubuntu 24.04** (reported with a log from Mint 22.3 "Zena"). Two bugs:
  1. **The venv was never finished.** The check was `import venv`, which succeeds on Debian/Ubuntu/Mint even when the `python3-venv` package is missing, because only `ensurepip` is split out there. So nothing was installed and `python3 -m venv` then failed with "ensurepip is not available". The check now targets `ensurepip` and installs the versioned package (`python3.12-venv` on Mint 22.x), falling back to `python3-venv`. If that still fails, a clear message with the manual command appears instead of an abort mid-run.
  2. **Eight lines of red apt errors for no reason.** PySide6 is only packaged from Debian 13 / Ubuntu 25.04 onwards; Ubuntu 24.04 "noble" — the base of Mint 22.x — only has PySide2. The script tried anyway. It now asks `apt-cache policy` first whether the packages exist at all, and quietly takes the venv route otherwise.
  3. **Qt refused to start: "Could not load the Qt platform plugin 'xcb'".** The PySide6 wheel ships Qt but not the system's X11 libraries — and on Ubuntu 24.04 (the base of Mint 22.x) exactly one of them, `libxcb-cursor0`, is missing from a default install. A distribution package would have pulled it in as a dependency; pip cannot know. On the pip route the script now installs the required X11 libraries and afterwards checks with `ldd` whether anything is still missing. If so, the package name is printed in plain text instead of an unexplained "core dumped".
* **`install.sh` works outside Arch** — the script called `sudo pacman -S git` without checking whether pacman exists at all, so on Fedora it stopped at "pacman: command not found". The package manager is now detected (pacman/dnf/apt/zypper) and PySide6 comes from the matching distribution package; if there is none, the installer builds its own venv, which touches neither the system Python nor PEP 668. The launcher wrapper now uses `python3` instead of `python` — Fedora only provides `/usr/bin/python` when `python-unversioned-command` is installed, so the app would have failed to start right after a successful install.
